Team 14 — Demonstration Video Shot List (v6 — Documentary Cut)

Target runtime: 9:53 (manual requires 8–10 min) · Due 19 June · 15% of final grade

Hard rules from the manual (check before every take):

  • No cable of any kind connected to the robots in ANY shot (Ethernet, USB, charger)
  • Required scenes: (1) avoiding cliffs, boundaries, mountains · (2) recognizing samples: size, color, surrounding temperature · (3) sending analysed info to base station + map gradually developed
  • Top-down presentation, motivation of design decisions, results AND failures

The narrative chain (this is the spine — every scene is one link): problems → how each is solved → why those choices (interviews) → making the pieces work together: prototypes and what went wrong → THE FULL ROBOT, revealed → the field. The robot is the destination of the entire first six minutes. It is never shown whole until 6.8 — the audience assembles it mentally, piece by piece, failure by failure, and only meets the finished machine seconds before watching it perform.

Reveal discipline (the rule that makes the structure work): before 6.8, the robot appears only in parts — sensor macros, wheel crops, board close-ups, defocused backgrounds. This includes interview b-roll: use GUI recordings, terminal output, hands-on-breadboard shots, and tight crops (wheel-level, sensor-level). If a moving robot must appear in b-roll, frame it partial or out of focus. Check every clip’s background for a stray full robot.

Three voices: NARRATOR (detached, retrospective; technical claims sourced from the final report) · INTERVIEWS (answering an unheard interviewer; Q-CAPs as small captions over the thinking beat) · THE FIELD (natural sound, narrator mostly silent).

5A — Electronics (2:38 – 3:08, 30s) — Ricky

Q-CAP: “How did you wire it all together?”

#DurShot
5.18sTalking head. Lower-third: RICKY — ELECTRONICS
5.28sB-roll: hands seating a sensor wire on the breadboard
5.37sB-roll: voltage divider close-up; multimeter probing
5.47sBack to talking head

Answer: “We mostly used the sensors given to us — the only addition was the IMU, for precise angle tracking through the mission. Everything fed into the breadboard, where we built circuits like voltage dividers to get the outputs we needed. Through UART and I2C, the raw sensor data reached the PYNQ board, ready for digital processing.”

5B — Algorithm (3:08 – 3:40, 32s)

Q-CAP: “How does it decide where to go?”

#DurShot
5.58sTalking head, lower-third: NAME — ALGORITHM
5.69sB-roll: GUI map showing the grid; cursor hovering cells
5.78sB-roll: screen recording of cells being marked explored/unsafe in sequence
5.87sBack to talking head

Answer (grounded in report §2.2, §3.2 — verify against navigation.c before filming): “We kept it deliberately simple. The field is split into fifteen-centimeter cells and statically partitioned — each robot gets its own region, with a one-cell buffer between them, so they never have to negotiate. Within its region, a robot explores depth-first: scan, move to the most promising unexplored cell, backtrack when an area is finished or unsafe. Everything it finds is logged to a cell and reported. We considered smarter strategies — but for a field this size, simple coverage beat clever coverage.”

5C — Communication & Networking (3:40 – 4:12, 32s)

Q-CAP: “How does it phone home?”

#DurShot
5.98sTalking head, lower-third: NAME — COMMUNICATION
5.109sB-roll: terminal with MQTT messages scrolling — an EVENT payload visible
5.118sB-roll: GUI updating live as messages arrive (screen only)
5.127sBack to talking head

Answer: “We defined a comma-separated text protocol — every message starts with its type: pose, field event, cell update, status. Easy to debug by eye, trivial to parse, and our messages were simple enough that anything fancier was complexity for its own sake. A C program handles the robot side, Python the base station — and a websocket bridges the MQTT data into the JavaScript the map runs on. Robot-to-robot chatter? Skipped. The partition made it unnecessary.”

5D — Embedded Software (4:12 – 4:42, 30s)

Q-CAP: “How do you make it move precisely?”

#DurShot
5.138sTalking head, lower-third: NAME — EMBEDDED SOFTWARE
5.148sB-roll: tight crop on a wheel accelerating smoothly from standstill (the ramping)
5.157sB-roll: tight crop, wheel-level, of a closed-loop turn finishing
5.167sBack to talking head

Answer: “We measured the wheels and the chassis and wrote the moving and turning functions from that — sixteen hundred steps per rotation gives you distance and angle for free. To stop the wheels from skipping, we added a ramping algorithm: speed builds gradually toward the target instead of jumping. And for turns, the IMU closes the loop — the robot rotates in small steps until the measured angle matches the commanded one.”

5E — User Interface (4:42 – 4:57, 15s)

Q-CAP: “And what does mission control see?”

#DurShot
5.177sTalking head, lower-third: NAME — USER INTERFACE
5.188sB-roll: screen recording — panning the map, clicking the start-mission button

Answer: “A web app — an HTML canvas drawing the field as a cell-based grid, each cell colored by status. It lives in the browser, updates live through the websocket, and can start the mission remotely. Everything the robots learn, you watch appear in real time.”
