## Datasets, Frameworks, and Neuromorphic Hardware

Rate encoding and latency encoding give an SNN two different ways to represent the same input, but the encoding choice only gains meaning inside a complete experiment. A useful evaluation therefore connects four layers: the dataset supplies the information, the encoding turns that information into spikes, the software framework simulates or trains the network, and the hardware platform executes the resulting computation. Each layer shapes what the experiment can reveal. Matching them begins with one concrete question: are we studying recognition quality, temporal processing, training behavior, memory use, energy use, or suitability for an event-driven application?

Imagine evaluating an SNN on a collection of ordinary images. Each image arrives as a fixed grid of pixel values, so time is absent from the original sample. The experiment must create a temporal representation before the SNN can process it. With rate encoding, a brighter pixel produces a spike train with a higher firing rate. The network observes several time steps and estimates intensity from the number or frequency of spikes. Repeated spikes provide many opportunities for downstream neurons to respond, which gives the learning process more activity from which to estimate gradients and makes the representation tolerant of occasional missing or misplaced spikes. The cost comes from the longer processing interval and the larger number of events.

Latency encoding assigns information to spike time. A stronger input can produce an earlier spike, while a weaker input produces a later one. In time-to-first-spike, or TTFS, encoding, each input neuron emits at most one spike for a sample. The network can therefore represent an image using fewer events and reach a decision over a shorter interval. A pixel with high intensity might fire near the beginning of the interval, while a dimmer pixel fires later. Their order carries the useful structure: "early" signals stronger evidence than "late." This sparse timing code supports fast and energy-conscious computation, while also giving the training procedure fewer spike events through which to adjust the network.

A conventional image benchmark is useful when the experiment asks how well an SNN architecture or training method handles a familiar static recognition problem. It provides controlled samples and labels, but its temporal spike structure comes from the selected encoder. As a result, an accuracy value measures the entire configuration: dataset, encoding scheme, architecture, learning rule, simulation duration, and other experimental choices. A result obtained with rate-coded images over many time steps answers a different question from a result obtained with TTFS encoding over a short interval. Accuracy values become meaningful when those conditions remain attached to them.

An event-based dataset begins closer to the operating language of an SNN. Its samples contain events associated with changes and times, so temporal structure belongs to the recorded data itself. Such a dataset fits questions about event-driven applications, dynamic inputs, sparse activity, or the use of spike timing. Speech and video illustrate why temporal structure can matter: the order and timing of changes contribute to the identity of the pattern. In this setting, collapsing all events into a static array may discard information that latency-sensitive processing could use. Preserving the event stream allows the experiment to test whether the network benefits from when events occur as well as where they occur.

Dataset selection should therefore follow the scientific question. A static benchmark can isolate architecture and training behavior under a chosen spike encoder. An event-based dataset can test how the network handles naturally temporal or change-driven inputs. Rate encoding is attractive when robust repeated activity and plentiful training signals are central to the study. Latency encoding is attractive when decision time, sparse firing, or energy-conscious operation is central. Dataset type alone does not dictate the encoding, because static and dynamic inputs can be transformed in several ways, yet the transformation must remain part of the interpretation.

**Question.** If latency encoding uses fewer spikes, should every low-energy experiment choose it automatically?

**Answer.** Latency encoding offers a strong starting point when low event counts and fast responses are experimental priorities, since a neuron may fire only once for each input. The learning method must also use spike timing effectively, and the dataset must preserve or receive a meaningful timing structure. Rate encoding can be preferable when repeated spikes provide the error tolerance and activity needed for stable gradient-based learning. The decision comes from matching the encoding's behavior to the experiment's goal.

The SNN software framework forms the next layer of the evaluation stack. It represents neuron dynamics, synaptic connections, spike propagation, time steps, and the selected training method. For an encoding comparison, the framework must express both the required spike-generation process and the learning procedure used with it. A rate-coded experiment needs enough simulated time to estimate firing activity, while a latency-coded experiment needs precise handling of spike order and first-spike times. If two configurations use different frameworks, observed differences may arise from implementation and simulation choices as well as from the encodings themselves. A clean comparison keeps the architecture, dataset treatment, and learning conditions aligned wherever the research question permits.

Framework choice also depends on whether the experiment studies learning or execution. A training study needs support for its selected method, such as backpropagation through time, surrogate-gradient learning, or a timing-based rule such as spike-timing-dependent plasticity. An execution study may focus on activity sparsity, memory efficiency, or event counts after training. These purposes place different demands on the software even when they use the same neuron model.

Neuromorphic hardware platforms add the physical execution layer. They are designed to exploit event-driven computation, where activity occurs in response to spikes. Sparse latency codes can fit this mode especially well because fewer spikes imply fewer event-triggered operations. Rate codes create repeated activity over a longer window, which can increase the work needed to represent one input. Yet an energy claim depends on the full hardware mapping, including the trained network, encoding, duration, activity pattern, and platform behavior. A software estimate of spike count supports one kind of conclusion; a measurement from a mapped hardware execution supports another.

**Question.** Can two SNNs be ranked by comparing their reported accuracy and energy numbers?

**Answer.** A fair ranking requires compatible experimental configurations. The dataset, architecture, encoding, learning method, number of time steps, framework, and hardware setting all influence the reported values. Comparisons become informative when they hold these conditions constant or explain how each difference affects the result. Without that context, the numbers describe separate systems answering separate questions.

Evaluation-stack compatibility ties the whole experiment together. Begin with the property being tested, choose a dataset that contains the relevant kind of information, select an encoding that exposes that information in spikes, use a framework that faithfully supports the encoding and training method, and choose neuromorphic hardware when physical event-driven execution is part of the question. The resulting mental model is a chain rather than a leaderboard: data becomes timed events, timed events drive learning and inference, software defines how those events are processed, and hardware determines how the event-driven workload behaves in practice.
